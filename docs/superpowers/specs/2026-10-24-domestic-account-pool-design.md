# 国产模型账号池设计

状态：已完成现状核对与设计自检，待用户确认方案后实施。

## 目标与默认范围

用户要求 LLMRouter 具备平台统一采购多个账号、向前端提供统一 API 的能力；首批主要接入国产模型。按供应商提供的 API Key（包括通过 API Key 调用的 Coding Plan）设计。登录 OAuth、Cookie 和浏览器自动登录不作为第一批凭据形式；如实际供应商要求其他授权，新增对应凭据适配器。

前端持续使用一个 LLMRouter API 地址、平台颁发的访问令牌和稳定的公开模型名。平台管理员管理供应商账号及其凭据，普通前端用户不需要选择或持有供应商 Key。

账号池中的成员应是拥有独立可用额度的账号。同一采购账号下创建多个 Key，不应被视为采购了多份额度；首批每个独立账号导入一份调用凭据，管理界面明确此约束。

## 已确认的现状

1. New API 的 `model/channel.go` 已有多 Key、随机/轮询、逐 Key 状态管理。核对快照 `33c61a24234aa20cb10e8a644304322c476361de`；这里没有与 OpenCodex 等价的统一账号冷却与恢复机制。
2. LLMRouter 已继承这些基础能力：`Channel.GetNextEnabledKey`、`ManageMultiKeys`、渠道权重/优先级、失败重试。不能把“已有轮询”直接等同于完整账号池。
3. LLMRouter 自有 `ProviderKeyPool` 还有独立的 Gateway 平台 Key 存储、LRU、冷却字段和状态管理；这些不覆盖所有原生国产模型适配器。
4. Gateway 冷却逻辑位于 `Adaptor.DoResponse`。常规 Chat 请求在 `TextHelper` 中遇到非 200 响应后直接返回错误，未进入 `DoResponse`，因此实际请求不能可靠触发那里处理的 429/401/403。不能只凭现有单元测试认定运行路径完整。
5. Gateway 当前 SQL 使用非 SQLite 一律 `FOR UPDATE SKIP LOCKED`，不满足项目 MySQL 5.7.8 / PostgreSQL 9.6 的最低兼容要求；本次涉及该选择器时需改为兼容的 GORM 行锁和 SQLite 回退。
6. 显式模型路由在一次失败后直接推进到下一个渠道候选，可能在当前渠道仍有健康账号时提前退出；普通渠道重试也没有请求级账号去重集合。
7. OpenCodex 具备静态 API Key 池的 429/401 处理、Retry-After、主动轮询、请求级失败成员身份及冷却；OAuth 账号池另有额度与会话逻辑。首批借鉴与 API Key 池有关的行为，不移植整个 OAuth 系统。

## 方案选择

推荐增强现有渠道多 Key 和 Gateway 平台 Key 两种入口，共用账号健康判定、失败分类和请求重试约束。供应商账号继续由现有适配器发起请求，复用公开模型路由、权限和计费。

另两种办法：每个账号单建渠道可以作为过渡，但难以统一账号冷却、可用数和同一请求的池内切换；把账号池完全交给 OpenCodex sidecar 则增加运行依赖，也无法由 LLMRouter 直接管理采购账号。这两种办法不作为首选。

### 1. 池与成员身份

- 一个池的成员必须使用相同供应商、端点、认证形式、协议与模型能力。相同模型字符串不足以证明账号可互换。普通 API 和 Coding Plan 若端点或授权能力不同，应建立不同池。
- 现有多 Key 渠道作为原生适配器的池；Gateway 使用现有 profile 下的平台 Key 池。渠道、profile 与模型路由的归属继续约束候选范围。
- 成员使用稳定、不含密钥的内部标识：多 Key 由渠道 ID 和凭据指纹关联，Gateway 由平台 Key 行 ID 关联。替换凭据、删除、重新排序不会把旧失败结果写给新成员。
- 新增 `upstream_account_states` 健康状态表保存成员标识、状态、冷却截止、固定原因码和更新时间；不重复保存明文凭据。使用 GORM、唯一键和数据库兼容类型，支持 SQLite/MySQL/PostgreSQL。现有手动禁用状态保持管理入口的权威性。
- 数据库持久化冷却与隔离状态；有 Redis 时加速共享读取并协调轮询，无 Redis 时使用数据库事务和兼容行锁。多实例不要求严格全局 A/B/A/B，但必须共享冷却、尊重暂停、避免重新使用已判定不可用成员。

### 2. 请求分配与池内切换

- 默认轮询健康成员；已有随机模式继续可用。管理员暂停、凭据失效、仍在冷却期的成员不参与正常选择。
- 同一次请求维护已尝试成员集合。仅在原有权限、分组、模型和协议候选范围内选择未尝试成员；先尝试当前池的健康成员，再按已有策略进入其他渠道候选。
- 每次真正发送都占用同一个请求尝试预算：使用现有 `RetryTimes + 1` 上限，不另加隐式无限循环。预算设为 0 时保留单次发送语义。后台说明如何按池规模配置预算。
- 暂时无可用成员时直接返回稳定的池不可用错误和可计算的最早 `Retry-After`，不在业务请求中等待长达数小时的额度恢复。仍有授权备用渠道时先尝试备用渠道。
- 请求取消、上游显式禁止重试、业务参数错误、权限固定路由、客户端已收到业务输出等情况继续遵守现有禁止重试规则。

### 3. 失败分类、冷却与恢复

- 429：记录实际发送成员的临时冷却，优先读取有效的 `Retry-After` 秒数或 HTTP 日期；未知恢复时间默认 60 秒，普通限流冷却上限 10 分钟。已认证且结构明确的额度重置时间可更长，最大 32 天；无可信重置信息时不虚构套餐额度。
- 供应商明确的余额/套餐耗尽：由供应商适配器根据结构化错误码分类。有可信重置时间则冷却到该时刻；无重置时间时先进入 1 小时资金冷却，之后允许真实请求重新检验，管理员充值后可立即恢复。不能仅凭任意消息关键字或 403 判定余额耗尽。
- 确认的无效/撤销凭据：只隔离失败成员，其他成员保持可用；管理员更换凭据或恢复后解除。
- 403 权限、模型未开通等：除非适配器确认是账号级凭据失效，否则不永久禁用整个账号。保留错误证据，按现有可重试规则处理。
- 网络故障或 5xx：不认定额度耗尽，不永久封禁成员。允许在原有预算、正文可重放和输出边界内尝试其他成员。
- 失败判定必须在非 2xx 早退前执行，并使用该次请求的成员快照；不读取稍后可能已被其他请求修改的“当前账号”。
- 冷却截止后自动重新获得选择资格，不需要人工重新启用或重启服务。成功请求清除该成员可恢复的临时失败记录，不清除管理员暂停。

### 4. 连续调用的安全边界

- 收到上游拒绝、尚未向前端输出业务正文时，允许透明换账号；不能把两次生成结果拼接成一条流。
- 已开始输出后断流：返回协议错误并标记失败，下次请求避开暂不可用账号。无法通用地在另一个账号续接已中断生成，不能宣称这一情况无感续传。
- Responses 的 `previous_response_id`、文件、缓存或服务端会话可能绑定供应商账号。保持现有作用域限制；有完整历史且现有机制支持重放才可重建，否则明确失败，不将账号 A 的私有状态交给账号 B。
- 首批自动切换覆盖同步对话与其流式请求。异步图像/视频/任务提交在没有供应商幂等契约时，不因不明确的网络结果自动重复提交；已建立的任务轮询必须继续使用创建任务的账号。
- 只对最终成功用量进行一次平台结算。预扣、补差、失败退款和审计继续使用现有原子计费会话；池内失败不新增一份前端扣费。供应商可能对已经执行但响应丢失的请求计费，平台不能承诺消除该上游行为。
- 所有成员均耗尽、被暂停或供应商整体中断时，返回真实可恢复状态，不承诺超出采购总容量的可用性。

### 5. 管理界面与 API

- 复用渠道多 Key 管理入口，增加“账号池”说明、可用/冷却/隔离/暂停数、成员脱敏标识、固定失败原因、恢复时间、手动恢复动作。
- Gateway 平台 Key 管理提供同等状态；普通用户 API 不暴露采购账号、Key、内部错误正文和成员指纹。
- 日志记录脱敏成员标识、池内切换次数、原因码与最终渠道，用于判断采购容量及故障；不记录完整请求头或密钥。
- 文案支持现有 i18n，保持权限与审计规则。没有配额查询接口的供应商明确显示“未知”，不能由轮询次数估算剩余额度。

## 验收场景

1. 三个独立账号连续请求分配到 A/B/C；禁用 B 后不再向 B 发送。
2. 同一次请求 A 返回 429，B 成功；前端只收到 B 的结果、平台仅结算一次；A 在冷却期内被后续请求跳过。
3. `Retry-After` 秒值、日期、无效值、超大值和额度重置边界均有确定预期；通过可控时钟验证到期回池，不使用长时间 sleep。
4. A 凭据失效只隔离 A；通用 403 不误封整个池；所有成员冷却时返回最早恢复提示，不形成无限重试。
5. 显式模型路由不会在 A 失败但 B 健康时直接耗尽当前池；不因池内重试越权跨组、跨协议或绕过上游 retry veto。
6. 前端已收到流式正文后失败不换账号拼流，取消后不继续发送，绑定账号的会话与任务不跨账号错用。
7. Gateway 的真实 HTTP 429/401 早退路径更新正确成员；BYOK 故障不进入平台账号池，不偷偷切到平台付费凭据。
8. 重启与缓存重载保留冷却，成员删除/替换后旧请求结果不污染新成员；两实例共享冷却状态。
9. SQLite/MySQL/PostgreSQL 均执行状态持久化、选择、锁与恢复回归；全量后端/race、前端构建和类型检查通过。

## 实施次序

1. 先补可复现缺口的真实 HTTP 回归，再实现健康状态、稳定成员身份与选择器。
2. 接入 controller 的池内重试及路由边界，修复 Gateway 的失败归因和数据库兼容选择器。
3. 补管理界面、恢复动作及操作文档；按实际接入供应商增加有来源的结构化错误分类。
4. 独立审查、跨数据库验证和完整检查通过后，合入本地分支。真实采购账号由管理员配置后，再执行不泄露凭据的实际调用验收。

设计自检：未承诺无限容量、跨账号断流续传或未知供应商的实时额度；未引入外部 sidecar 依赖；没有重复建设凭据存储或钱包；生产实施尚未开始。
