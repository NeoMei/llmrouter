# LLMRouter v0.1.0-rc.31

在 rc.30 的基础上补一处：供应商已完成、但结果文件已被上游删除（返回 403）的 OCR 任务，原来会每 10 秒重试一次并永远失败，预留在 UniHub 侧一直挂着。生产上正好有 4 条这样：`provider_state=done`、`billing_state=reserved`、结果资源为空，PaddleOCR 的结果地址现在返回 403。

修复分两处：下载路径把 403/404/410 归类为 `errResultGone`；`Status` 对 `errResultGone` 与 `ErrOCRConflict`（结果地址不在该任务登记的原产地内，历史上存在 `paddleocr-store-6` 变体）都直接按 failure 结单并退款，不再重试。拿不到的输出不能收费，预留必须退回。真正的瞬时失败（网络抖动、大小超限）仍然重试。

rc.30 的内容保持不变：提交供应商没有任何确定答复（超时/断连）的预留，由 `ReleaseStaleSubmission` 在 15 分钟宽限后转为 `rejected` 并走既有退款路径；OCR 新增 cancel 接口；`Finish` 仍拒绝 `uncertain`。

This release adds one fix on top of rc.30: an OCR job the supplier completed, whose result file the upstream already deleted (403), used to retry every ten seconds and fail forever, leaving the reservation held. Four production jobs were in exactly that state — `provider_state=done`, `billing_state=reserved`, empty result resource, PaddleOCR result URLs now answering 403.

Two changes: the download path classifies 403/404/410 as `errResultGone`, and `Status` completes a job as a failure and refunds for both `errResultGone` and `ErrOCRConflict` (a result URL outside the origins recorded for the job — the `paddleocr-store-6` variant exists in production). Output nobody can fetch must not be charged, and the reservation has to return. Other failures — network, size limit, signature mismatch — still retry.

rc.30 is unchanged: a reservation whose submission never got any definite answer is released by `ReleaseStaleSubmission` after a 15 minute grace, recorded as `rejected` and refunded through the existing path; OCR gains cancel endpoints; `Finish` still refuses `uncertain`.
