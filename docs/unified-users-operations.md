# UniHub 接入后的原用户、管理员、额度和 API Key

适用于 LLMRouter `0.1.0-rc.11` 与 UniHub `0.4.11`。接入后继续使用 LLMRouter 原来的页面和接口；UniHub 用户与原产品用户在相同角色、资源、配置和资金条件下具有相同功能。

## 登录与注册

直接打开 LLMRouter 原来的 `/sign-in` 和 `/sign-up`。密码、OAuth、MFA、Passkey 和恢复流程仍由原产品完成，不要求用户改用另一套精简页面。已有 UniHub 浏览器会话时可自动进入；没有会话或自动登录暂时失败时返回原登录表单，不反复跳转。

原入口完成全部认证因素后，可建立 UniHub 中央浏览器会话，再进入其他已接入产品，无需再次注册登录。首次通过中央身份进入本产品时，执行本产品的新用户策略，包括默认设置、配置的注册赠额和默认 Key；重新进入或中断恢复不会重复发放。

旧用户仍使用原账号和原认证器，原用户 ID、Key、设置、分组和历史记录保留。已核实的身份映射连接原用户与中央身份，不凭用户名或邮箱自动合并两个账号。不要为了接入 UniHub 再给旧用户创建一套平行账号。

## 管理员与开用户

具有本产品用户管理权限的管理员，继续在原 `/users` 页面新增、查看、启用、停用和管理用户。角色及细粒度权限由 UniHub 当前产品、当前实例的授权决定；原 SQL 中缓存的管理员角色不能覆盖中央撤权。

原管理员接入时，应按审核过的原用户 ID、认证版本和角色进行显式导入。普通注册不会自动获得管理员权限，也不能从邮箱相同推导管理员身份。产品角色 `1`、`10`、`100` 对应原普通用户、产品管理员和产品 root；它们不是 UniHub 全局管理员角色。

UniHub 用户管理界面可为目标用户和产品实例分配已声明的产品角色。产品管理员、财务权限和 UniHub 全局用户管理权限分别授权。查看产品日志不会自动获得财务管理权限。全局用户管理员的 `USER_ADMIN_IDS` 必须使用已核实的中央用户 UUID，不能使用 LLMRouter 的用户名或原用户编号。

## 额度与预算

原用户页的增加、减少、设置剩余额度继续具有原含义：调整用户可消费额度。对于已经切换中央资金的账号，该操作写入 UniHub 的最终账本，并通过原页面显示。提高预算上限不会增加余额。

中央适配的原额度资产为当前 LLMRouter 实例的 `LR_QUOTA/0`，单位版本 `lr-quota-v1`。它保留产品原额度数值与显示规则，不自动成为可提现现金，也不自动成为其他产品或实例的余额。普通 Key 的剩余额度、账户预算和单次限额继续作为约束。

新账号若按部署策略初始额度为零，管理员可在原用户页按原规则增加额度。充值、兑换、签到和已购套餐继续使用原流程；中央账号使用可恢复收据交付额度，支付确认与额度入账分别展示。套餐内消费消耗原权益，不重复扣钱包。

## 创建和使用 API Key

进入原 `/keys` 页面创建 Key。原模型限制、IP 白名单、分组、跨组重试、有效期、状态和额度字段保留，不因使用 UniHub 身份而换成另一种简化 Key。保管密钥时继续遵循原页面的显示和安全规则。

原 Key 继续使用本实例的标准 `/v1` 等兼容 API。调用仍经过原渠道选择、协议适配、计量和价格计算。中央身份和权限在受保护请求中重新核对；Key 被禁用、过期或撤销后，新调用被拒绝。

已经提交的调用和异步任务仍按原用户、原 Key、原付款账号和原价格完成结算或退款。撤权不抹掉已经发生的费用，费用恢复不会重新发送供应商请求。未知结果保留原调用和待对账记录，不能通过换 Key、换账号或切回旧钱包跳过结算。

## 流量与费用查询

原概览、模型分析、流量、日志和任务页面继续使用。记录按原产品用户及 Key 归属展示；中央账号的余额读取最终账本，SQL 中本地余额归零不代表调用免费。

重复提交同一结算或费用调整不得重复扣款。临时服务故障时显示待确认状态；支付已经确认但额度尚在入账时，不要重复支付。

## 本次旧账号的资金处理

本次上线对所有旧账号仅做经过核实的身份映射，保留其原资金后端和数值；历史大余额继续留在原系统，不截断、不清零、不隐式转换。旧账号的原 Key 和调用继续使用原资金所有权。身份映射本身不等于完成余额迁移。

新注册或首次进入的新用户可使用中央资金适配。旧账号后续切换中央资金，须单独完成全写节点停机、批量账核对、缓存与 SQL 核对、未终态调用及退款责任核对、备份还原验证，再使用审核过的离线导入清单。`product-runtime-migrate-linux-amd64` 默认只校验快照；`-apply` 才会写入。

离线清单中的 `offline_evidence` 是操作方提供的外部审计证据，不是 CLI 自动检测所有旧节点已退出的证明。`drained: true` 单独不够。不要删除未知 lease、伪造核账记录、按邮箱批量合并，或为了通过迁移而截断历史余额。

## 部署配置与凭据

浏览器跳转和服务端 API 使用不同地址。本次部署保留既有旧平台账务地址，配置如下；地址属于部署配置，凭据必须另由受限配置文件提供：

```dotenv
UNIHUB_ORIGIN=https://unihub.quukk.com:18488
UNIHUB_PRODUCT_API_ORIGIN=https://unihub.quukk.com:18488
UNIHUB_PRODUCT_PUBLIC_ORIGIN=https://unihub.quukk.com
```

`UNIHUB_ORIGIN` 保留旧平台调用所需的私有 TLS 入口，`UNIHUB_PRODUCT_API_ORIGIN` 用于新用户、授权和资金服务端适配；浏览器始终使用 `UNIHUB_PRODUCT_PUBLIC_ORIGIN` 公共 HTTPS 入口。不得把浏览器回调导向内部 API 端口，也不得让内部请求经过公共站点的 `/internal` 拒绝规则。

新的产品 runtime service token 必须按产品、实例和操作范围单独授权，保存在后端。新增该凭据不代表轮换或删除原平台、数据库、会话和供应商凭据。普通 runtime 凭据不拥有审核导入权限；身份导入使用独立的受限迁移凭据。自动计费恢复需要经过审核的 `calls:refund`、`calls:reprice` 等操作授权。

服务地址、产品或实例变更会影响已经冻结的资金归属，不能直接修改配置绕过待结算记录。进一步协议和两种产品接入方式见 UniHub 配套源码包中的 `docs/userkit/runtime-adapter.md` 与 `docs/userkit/account-integration-modes.md`。
