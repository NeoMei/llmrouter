# LLMRouter / UniHub integration

Approved by the user on 2026-10-25 after the source investigation. Implement the existing gateway first, then unified identity, personal/team billing UI, and scoped cross-product reporting. This authorizes local implementation and acceptance; production cutover and real merchant activation are separate release operations.

## Ownership

UniHub owns end-user identity, account membership/finance authorization, product charging profiles, subscriptions, recharge posting, wallets, model credit allocations and final charges. LLMRouter owns its product UI, model/provider routing, channel/account-pool operations and trusted usage collection. Platform traffic must never debit LLMRouter local user/token quota, purchase local subscriptions or use its local payment posting paths. Existing local accounts/keys continue their existing path until explicitly migrated; no automatic identity/email or balance migration. Operator privileges are never derived from a UniHub business role.

## Product identity and UI

Use UniHub headless registration + password/S256 PKCE login with a fixed registered llmrouter client/redirect/Origin; passwords are only sent to the fixed UniHub identity endpoint. A distinct product integration module holds access tokens in memory (no local/session storage) and clears all user/account/query state on logout or expiry. Preserve local operator login. Add a discoverable UniHub entry to login and wallet surfaces, showing its own product UI rather than embedding the UniHub console.

Provide an authenticated proof exchange that validates the product token against the fixed UniHub service and projects identity by fixed issuer plus returned immutable user ID, never by email. Validation must require `/v1/capabilities` kind=product, product_id=llmrouter and exact configured client_id alongside `/v1/me`, since me alone also accepts other product/console tokens. Prefer a request-scoped projection and an independent `/unihub` route; no local User or login session is needed. If mapping to local users is used, create only a common business projection, never attach an existing user by email/name, never grant admin, and reject local financial or local API-key operations for that projection. A UniHub token, a local dashboard session and a model credential are different capabilities. Current selected personal/team account is always explicit and reauthorized by UniHub on every business operation. The UI lists accounts, resources, subscriptions/catalog, recharge/order status and usage, supports team creation/invitations and selecting the payer, and issues short-lived task/model credentials for the gateway. Never mislabel these as durable API keys. Existing local keys/balances remain separate and require an explicit later migration.

All money/usage quantities are canonical integer strings, rendered without Number loss. Finance actions are visible only to owner/billing_admin; membership administration follows owner/admin. Account switching cannot mix stale query results or submit an action for a previous account. Financial writes require explicit stable idempotency keys, preserved through pending/error state and readback; never auto sandbox-settle or present an order as paid just because creation succeeded. Real payment unavailable must be shown honestly. Subscription upgrade and addon choices follow UniHub immutable offers/profile, never a second local plan model.

## Unified model reporting

Add explicit `usage:all-products` product scope, restricted at registry validation to product `llmrouter`. Add separate model-pool account calls/detail/summary endpoints requiring both this scope and current owner/billing_admin role. Optional origin filter restricts results but cannot widen ordinary product endpoints. Reuse ledger-backed query, pagination/account binding and asset grouping; never expose provider cost, credentials or prompts. Existing product query isolation stays unchanged. Extend OpenAPI and SDK with named methods for these explicit endpoints. LLMRouter finance UI uses them when configured, and handles missing scope with its ordinary own-origin view without claiming completeness.

The product shell presents UniHub resources and requires current UniHub authorization; native refresh cookies never authorize UniHub operations.
