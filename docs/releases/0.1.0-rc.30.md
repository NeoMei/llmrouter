# LLMRouter v0.1.0-rc.30

本次修复 OCR 预留泄漏：供应商提交没有拿到确定答复时，预留在 UniHub 侧永久挂在 RESERVED，用户额度被锁住而无法释放。生产上已积累 16 条（chat 与 OCR 都有），本次一并修复并自动回收。

根因：`Create` 里 `Reserve` 成功之后，若提交供应商以超时或断连结束（没有 HTTP 状态码），代码只记录 `RecordSubmission(..., uncertain)` 就返回错误，既不落 `Decision` 也不调用 `Finish`。这类任务没有 provider job id，`Finish` 拒绝 `uncertain`，后台恢复 worker 只挑已进入终态的 provider 状态，因此永远不会有任何路径释放它；平台侧的 OCR 取消接口此前直接返回 501。

修复内容：

- 新增 `ReleaseStaleSubmission`：只对 `submission_state=uncertain`、`billing_state=reserved`、无 provider job id、无 decision 的任务生效，把它记为 `rejected` 后走既有的 `Finish(failure)` 退款路径。`Finish` 本身仍拒绝 `uncertain`，调用方原有的「不确定不得退款」保证不变。
- 超时宽限 15 分钟：提交刚失败时仍可能在上游运行，宽限期后才释放。
- OCR 后台 worker 增加「有预留但没有 provider job id」的扫描分支，直接释放而不去轮询一个不存在的任务。
- 新增 `POST /api/v2/ocr/jobs/{id}/cancel` 与 `POST /v1/ocr/{id}/cancel`，任务所有者可主动放弃供应商从未接收的任务，立即退额；已拿到 provider job id 的任务仍然不可这样取消。

取舍：把 `uncertain` 当作 `rejected`，等于判定「这次发送没有执行」。如果上游其实执行成功，用户会得到一次免费结果；方向是宁可不收、绝不重复扣款。

This release fixes an OCR reservation leak: when the supplier submission returned no definite answer, the reservation stayed RESERVED on the UniHub side forever, locking the user's quota with no way to release it. Production had accumulated 16 such rows (chat and OCR alike); this release fixes the cause and lets them drain automatically.

Root cause: after a successful `Reserve`, a submission that timed out or lost its connection (no HTTP status) only recorded `RecordSubmission(..., uncertain)` and returned the error — no `Decision`, no `Finish`. Such jobs have no provider job id, `Finish` refuses `uncertain`, and the recovery worker only selects terminal provider states, so nothing ever released them; the platform OCR cancel route answered 501.

Changes:

- New `ReleaseStaleSubmission` acts only on `submission_state=uncertain`, `billing_state=reserved`, no provider job id and no decision: it records `rejected` and refunds through the existing `Finish(failure)` path. `Finish` still refuses `uncertain`, so the existing "uncertain never refunds" guarantee for callers is unchanged.
- A 15 minute grace period, because a fresh submission may still be running upstream.
- The OCR background worker also selects reservations without a provider job id and releases them instead of polling a job that does not exist.
- New `POST /api/v2/ocr/jobs/{id}/cancel` and `POST /v1/ocr/{id}/cancel`: an owner may abandon a job the supplier never accepted and get the quota back immediately; a job with a provider job id still cannot be cancelled this way.

Trade-off: treating `uncertain` as `rejected` decides that the send did not execute. If the supplier did run it, the user receives one uncharged result. The direction is to undercharge rather than double-charge.
