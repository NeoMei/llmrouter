# 国产多模态模型统一接入与账号池设计

状态：已完成现状核对与设计自检，待用户确认方案后实施。

## 目标与默认范围

用户要求 LLMRouter 具备平台统一采购多个账号、向前端提供统一 API 的能力，且首批不只覆盖 Coding：必须覆盖主流国产模型的文本、图片、语音、视频理解和 OCR。图片同时纳入理解、生成与编辑，语音纳入识别/转写、理解与合成；视频理解是明确交付项，不以已有视频生成接口替代。保留并纳管已有视频生成任务，新增生成供应商不占用视频理解的优先级。

按供应商提供的 API Key（包括可调用对应能力的 Coding/Token Plan）、App ID + Token 等正式 API 凭据设计。凭据结构不能被限制成一个 Bearer 字符串，必须复用供应商适配器要求的认证形式。登录 OAuth、Cookie 和浏览器自动登录不作为第一批凭据形式；如实际供应商要求其他授权，新增对应凭据适配器。不依据套餐名称推断它支持所有多模态接口，开通能力、端点、额度和计费归属须分别核对。

前端持续使用一个 LLMRouter API 地址、平台颁发的访问令牌和稳定的公开模型名。平台管理员管理供应商账号及其凭据，普通前端用户不需要选择或持有供应商 Key。

账号池中的成员应关联真实采购账号及配额作用域。同一采购账号下创建多个 Key，不应被视为采购了多份额度；首批默认每个独立账号导入一份调用凭据，管理界面明确此约束。支持为确实共享余额或限额的成员配置同一个 quota group；共享账户余额与各操作独立 RPM/并发额度分开建模，避免盲目叠加容量或过度冷却。

本次范围从“同步对话账号池”扩展为“共享账号池基础 + 多模态能力目录 + 各类适配器与资源生命周期”。按模块分段实施、分别验收，不能先交付文本轮询就宣称整个多模态目标已完成。

## 已确认的现状

1. New API 的 `model/channel.go` 已有多 Key、随机/轮询、逐 Key 状态管理。核对快照 `33c61a24234aa20cb10e8a644304322c476361de`；这里没有与 OpenCodex 等价的统一账号冷却与恢复机制。
2. LLMRouter 已继承这些基础能力：`Channel.GetNextEnabledKey`、`ManageMultiKeys`、渠道权重/优先级、失败重试。不能把“已有轮询”直接等同于完整账号池。
3. LLMRouter 自有 `ProviderKeyPool` 还有独立的 Gateway 平台 Key 存储、LRU、冷却字段和状态管理；这些不覆盖所有原生国产模型适配器。
4. Gateway 冷却逻辑位于 `Adaptor.DoResponse`。常规 Chat 请求在 `TextHelper` 中遇到非 200 响应后直接返回错误，未进入 `DoResponse`，因此实际请求不能可靠触发那里处理的 429/401/403。不能只凭现有单元测试认定运行路径完整。
5. Gateway 当前 SQL 使用非 SQLite 一律 `FOR UPDATE SKIP LOCKED`，不满足项目 MySQL 5.7.8 / PostgreSQL 9.6 的最低兼容要求；本次涉及该选择器时需改为兼容的 GORM 行锁和 SQLite 回退。
6. 显式模型路由在一次失败后直接推进到下一个渠道候选，可能在当前渠道仍有健康账号时提前退出；普通渠道重试也没有请求级账号去重集合。
7. OpenCodex 具备静态 API Key 池的 429/401 处理、Retry-After、主动轮询、请求级失败成员身份及冷却；OAuth 账号池另有额度与会话逻辑。首批借鉴与 API Key 池有关的行为，不移植整个 OAuth 系统。
8. `relay/capability/operation.go` 已定义图片生成/编辑、转写、TTS 等操作，但缺少独立 OCR 操作；视频操作为生成/查询任务，不能据此推断视频理解受支持。图像/视频理解可通过具备相应输入能力的 Chat/Responses 模型接入，仍须验证请求载体和供应商能力。
9. `dto/openai_request.go` 有 image/audio/video 内容类型，`service/modelcatalog/catalog.go` 的公开模型元数据主要描述上下文、reasoning 与工具，没有完整的多模态输入/输出和媒体约束契约。
10. `relay/capability/defaults.go` 的图片/语音白名单没有覆盖若干已有国产适配器：Ali 已有图片生成/编辑转换但其音频转换明确不支持，MiniMax/VolcEngine 已有 TTS 分支却不意味着支持 ASR。需要逐操作核验注册与实现的一致性，不能整类放开后由下游报错。
11. `TaskPrivateData.Key` 与部分查询路径已有创建账号快照机制，但 `InitTask` 当前只为部分渠道保存凭据。多模态任务需要统一绑定实际成员，不能默认用渠道当前 Key 或整个多 Key 字符串查询。
12. 按用户要求核对本地 `SuperWagie-open` 的资料库与统一模型配置。当前资料库消费 Embedding、Rerank、视觉理解和 PaddleOCR；ASR 模型可由旧安装导入，但扫描器尚未接收音视频，图文向量列为 planned。为这项实际下游需求增加兼容性验收，详见第 9 节。读取该项目未修改其源码或现有配置，也没有读取用户模型凭据。

## 方案选择

推荐增强现有渠道多 Key 和 Gateway 平台 Key 两种入口，共用账号健康判定、失败分类和请求重试约束。供应商账号继续由现有适配器发起请求，复用公开模型路由、权限和计费。统一的是访问地址、身份认证、模型目录、账号调度、任务管理和计费；图像、音频二进制、OCR 结构结果及异步任务仍有各自明确的 API 契约，不强制压成文本聊天返回值。

另两种办法：每个账号单建渠道可以作为过渡，但难以统一账号冷却、可用数和同一请求的池内切换；把账号池完全交给 OpenCodex sidecar 则增加运行依赖，也无法由 LLMRouter 直接管理采购账号。这两种办法不作为首选。

### 1. 池与成员身份

- 一个池的成员必须使用相同供应商、端点和认证形式；每次再按协议、操作、输入模态、模型授权与资源访问能力过滤成员。相同模型字符串不足以证明账号可互换。普通 API 和 Coding Plan 若端点或授权能力不同，应建立不同池。
- 现有多 Key 渠道作为原生适配器的池；Gateway 使用现有 profile 下的平台 Key 池。渠道、profile 与模型路由的归属继续约束候选范围。
- 成员使用稳定、不含密钥的内部标识：多 Key 由渠道 ID 和凭据指纹关联，Gateway 由平台 Key 行 ID 关联。替换凭据、删除、重新排序不会把旧失败结果写给新成员。
- 新增 `upstream_account_states` 健康状态表保存成员标识、作用域、状态、冷却截止、固定原因码和更新时间；作用域区分账号全局、共享配额组与模型/操作。无效凭据可作用于全账号，语音 RPM 限制不误伤文本，已确认共享资金耗尽才作用于相应共享配额组。不重复保存明文凭据。使用 GORM、唯一键和数据库兼容类型，支持 SQLite/MySQL/PostgreSQL。现有手动禁用状态保持管理入口的权威性。
- 数据库持久化冷却与隔离状态；有 Redis 时加速共享读取并协调轮询，无 Redis 时使用数据库事务和兼容行锁。多实例不要求严格全局 A/B/A/B，但必须共享冷却、尊重暂停、避免重新使用已判定不可用成员。

### 2. 请求分配与池内切换

- 默认轮询健康成员；已有随机模式继续可用。管理员暂停、凭据失效、仍在冷却期的成员不参与正常选择。
- 同一次请求维护已尝试成员集合。仅在原有权限、分组、模型、协议、操作与输入模态候选范围内选择未尝试成员；先尝试当前池的健康成员，再按已有策略进入其他渠道候选。跨供应商替代必须由管理员显式配置到同一公开能力路由，且返回契约兼容；不因某家池空就暗中换模型。
- 每次真正发送都占用同一个请求尝试预算：使用现有 `RetryTimes + 1` 上限，不另加隐式无限循环。预算设为 0 时保留单次发送语义。后台说明如何按池规模配置预算。
- 暂时无可用成员时直接返回稳定的池不可用错误和可计算的最早 `Retry-After`，不在业务请求中等待长达数小时的额度恢复。仍有授权备用渠道时先尝试备用渠道。
- 请求取消、上游显式禁止重试、业务参数错误、权限固定路由、客户端已收到业务输出等情况继续遵守现有禁止重试规则。

### 3. 失败分类、冷却与恢复

- 429：记录实际发送成员及已确认限额作用域的临时冷却，优先读取有效的 `Retry-After` 秒数或 HTTP 日期；未明确作用域的请求限流先作用于当前模型/操作，不推断整账号全部能力耗尽。未知恢复时间默认 60 秒，普通限流冷却上限 10 分钟。已认证且结构明确的额度重置时间可更长，最大 32 天；无可信重置信息时不虚构套餐额度。
- 供应商明确的余额/套餐耗尽：由供应商适配器根据结构化错误码分类。有可信重置时间则冷却到该时刻；无重置时间时先进入 1 小时资金冷却，之后允许真实请求重新检验，管理员充值后可立即恢复。不能仅凭任意消息关键字或 403 判定余额耗尽。
- 确认的无效/撤销凭据：只隔离失败成员，其他成员保持可用；管理员更换凭据或恢复后解除。
- 403 权限、模型未开通等：除非适配器确认是账号级凭据失效，否则不永久禁用整个账号。保留错误证据，按现有可重试规则处理。
- 网络故障或 5xx：不认定额度耗尽，不永久封禁成员。只有该操作满足已定义的重放策略时，才允许在原有预算与输出边界内尝试其他成员。未收到正文不代表供应商没有执行、没有计费，图片生成和任务创建尤其不能仅按 HTTP 状态盲目重试。
- 失败判定必须在非 2xx 早退前执行，并使用该次请求的成员快照；不读取稍后可能已被其他请求修改的“当前账号”。
- 冷却截止后自动重新获得选择资格，不需要人工重新启用或重启服务。成功请求清除该成员可恢复的临时失败记录，不清除管理员暂停。

### 4. 连续调用的安全边界

- 收到上游明确拒绝执行、尚未向前端输出业务正文且操作允许重放时，可以透明换账号；不能把两次生成结果拼接成一条流。超时、断连或 5xx 后执行状态不明时，由操作策略及供应商幂等契约决定，不把“尚未收到正文”等同于“可安全重放”。
- 已开始输出后断流：返回协议错误并标记失败，下次请求避开暂不可用账号。无法通用地在另一个账号续接已中断生成，不能宣称这一情况无感续传。
- Responses 的 `previous_response_id`、文件、缓存或服务端会话可能绑定供应商账号。保持现有作用域限制；有完整历史且现有机制支持重放才可重建，否则明确失败，不将账号 A 的私有状态交给账号 B。
- 首批对所有纳入的模态执行统一健康选择与失败归因，自动重试按操作分别启用。同步理解/OCR/转写支持在完整输入可重放、资源可访问、尚无输出且满足重放策略时换成员；图像生成/编辑、异步转写/文档解析/视频任务提交在没有供应商幂等契约时，不因不明确的网络结果自动重复提交。
- 已建立任务的状态查询、结果下载、取消（若支持）必须继续使用创建任务的实际账号或它更新后的同身份凭据，不参加普通轮询。任务内持久化稳定成员、供应商任务 ID 和必要认证引用；普通用户视图不暴露这些内部数据。
- 只对最终成功用量进行一次平台结算。预扣、补差、失败退款和审计继续使用现有原子计费会话；池内失败不新增一份前端扣费。供应商可能对已经执行但响应丢失的请求计费，平台不能承诺消除该上游行为。
- 所有成员均耗尽、被暂停或供应商整体中断时，返回真实可恢复状态，不承诺超出采购总容量的可用性。

### 5. 管理界面与 API

- 复用渠道多 Key 管理入口，增加“账号池”说明、可用/冷却/隔离/暂停数、成员脱敏标识、固定失败原因、恢复时间、手动恢复动作。
- Gateway 平台 Key 管理提供同等状态；普通用户 API 不暴露采购账号、Key、内部错误正文和成员指纹。
- 日志记录脱敏成员标识、池内切换次数、原因码与最终渠道，用于判断采购容量及故障；不记录完整请求头或密钥。
- 文案支持现有 i18n，保持权限与审计规则。没有配额查询接口的供应商明确显示“未知”，不能由轮询次数估算剩余额度。

### 6. 多模态能力目录与统一接口

| 能力 | 前端契约 | 模型与账号选择条件 | 首批输出 |
| --- | --- | --- | --- |
| 文本/Coding | 现有 Chat / Responses / Messages | 文本、工具、上下文及协议能力 | 文本或流式事件 |
| 文本向量 | `/v1/embeddings` | 固定向量空间、维度、编码、批量与 query/document 语义 | 顺序与 index 正确的数值向量 |
| 检索重排 | `/v1/rerank`，并提供下游所需的阿里兼容入口 | query/documents、top_n、返回分数及原文选项 | 原始文档 index 与相关性分数 |
| 多模态向量 | 显式声明的原生或扩展 Embedding 契约 | 图片/文本/视频输入类型、向量空间与版本 | 带明确定义维度与语义的向量 |
| 图片理解 | Chat / Responses 中的图像内容 | image 输入、图片数量/格式/像素限制 | 描述、问答或明确配置的 JSON |
| 图片生成/编辑 | 现有 `/v1/images/generations`、`/v1/images/edits` | image 输出、编辑参考图、尺寸与数量限制 | 兼容的图像结果；异步供应商通过任务契约适配 |
| 语音识别/转写 | `/v1/audio/transcriptions`，长音频使用任务契约 | 音频格式、时长、语言及同步/异步能力 | 文本；有来源支持时提供片段、时间戳与说话人 |
| 语音理解 | 支持音频输入的 Chat / Responses 模型 | audio 输入，和 ASR/TTS 分别声明 | 音频语义问答/结构化结果 |
| 语音合成 | `/v1/audio/speech` | TTS、音色、编码、采样率及流式能力 | 音频二进制或已声明流式格式 |
| 视频理解 | 支持视频的 Chat / Responses 内容，必要时绑定上传资源 | video 输入、抽帧参数、时长、格式；是否理解音轨单独声明 | 摘要、场景问答和支持的时间定位结果 |
| OCR/文档解析 | 新增 LLMRouter 明确定义的 `/v1/ocr`；兼容 Chat 的 OCR 模型也保留原路径 | 图片/PDF、页数、版面解析及结构化能力 | 文本/Markdown；结构能力可含页码、文本块、表格或公式 |

`/v1/ocr` 是 LLMRouter 扩展接口，不宣称它是 OpenAI 标准。请求携带公开模型名、受支持的文件/图片来源及输出选项；结果保留供应商确实返回的结构信息，不能制造 bbox、confidence、页码或时间戳。大文档及长音频异步任务使用统一任务状态封装，并保留供应商扩展字段，避免伪装成已完成的同步结果。

公开模型目录补充 `input_modalities`、`output_modalities`、支持操作、同步/异步、流式、媒体格式与大小/数量/时长/页数限制。目录只展示已配置且授权可用的能力；供应商拥有该能力、适配器有对应方法、当前账号已开通这三件事分别验证。不得因为所有请求都进入 Chat 路由，就把纯文本模型标成支持图片/视频。

### 7. 供应商接入矩阵

按厂商平台和能力族建立可扩展矩阵，不把“支持主流国产模型”写成永久支持所有新模型的承诺。首批覆盖阿里百炼/通义、火山方舟/豆包及其语音服务、智谱、MiniMax 的相关能力；腾讯混元、百度千帆、阶跃星辰、硅基流动等进入同一登记和适配机制，逐项按官方契约及采购需求接入。具体模型 ID、地域、版本、价格不在设计中猜测，实施时以官方文档和当前账号授权确认，并可在后台更新。

- [GLM-OCR](https://docs.bigmodel.cn/cn/guide/models/vlm/glm-ocr)：PDF/图片输入及文档解析输出，需要独立于普通视觉问答处理。
- [MiniMax 同步语音合成](https://platform.minimax.cn/docs/api-reference/speech-t2a-http)：TTS 有原生语音参数及二进制/流式输出契约。
- [MiniMax 账号限流说明](https://platform.minimaxi.com/document/Rate%20limits?key=66b19417290299a26b234572)：主/子账号可共享限额，不能按 Key 数乘出可采购容量。

以上来源用于能力和接口设计，不表示仓库中的适配器已通过这些服务的实测。首批验收按能力族组织，至少每类有一条完整适配路径；不能用某家 TTS 通过替代 ASR 验收，也不能用一张图片问答通过替代 PDF/OCR 或视频理解验收。

### 8. 媒体、状态与计费

- URL、Base64、multipart 与供应商 File ID 分别验证；转发保留媒体内容及受支持的 `fps`、分辨率、音色等语义，无法无损转换时明确拒绝，而非丢字段后当纯文本请求发送。
- 本地上传由有租户/用户权限和到期清理的托管资源承载。File ID、音色克隆、文档任务及输出下载若绑定供应商账号，记录成员作用域，换账号时重新上传或明确拒绝。客户端不能传任意本地路径让服务器读取。
- 服务器拉取 URL 复用并检查现有受控下载路径：限制大小、重定向、超时与允许目的地；不得为支持新媒体绕过已有内网/元数据地址访问保护。
- 单次图像数量、尺寸、音频/视频时长、PDF 页数和请求总大小在预扣前检查；声明值和解码/上游元数据都视为不可信，使用现有统一计费上限与饱和转换，不另写裸浮点转整数。
- 用量按实际支持的 token、图像张数/规格、音频时长/字符、视频时长、OCR 页数或供应商明确的请求单位结算，不统一虚算为文本 token。复用现有对应计费路径；缺少可信计费定义的能力先不上线收费。
- 厂商任务已创建后持久化再进行轮询/回调；任务状态推进、退款与差额结算使用幂等更新。保留超时但执行状态不明的中间状态和对账路径，避免将模糊网络失败直接退款后再次创建同一任务。

1. 提供受统一令牌鉴权的兼容入口，让现有知识后端指向 LLMRouter。Embedding/视觉提供 `/v1` 及已声明的 compatible-mode 路径；Rerank 提供阿里 `/api/v1/services/rerank/text-rerank/text-rerank` 兼容路径；PaddleOCR 保持其 v2 jobs 契约。内部仍复用同一账号池、权限、审计和计费，不直接做任意 URL 反向代理。

3. 现有索引绑定 Embedding 名称、base URL 和维度。即使只是把供应商直连改为网关地址，也会触发 SuperWagie 的更换保护。上线必须显式处理这一迁移：新库可直接使用 LLMRouter，旧库经管理员确认进行一致性验证和迁移/重建；本次不改 SuperWagie 的保护检查，也不自动重建用户资料库。
4. 同一个向量公共模型 ID 必须绑定实际模型、版本、维度、预处理及 query/document 语义。不能因账号限流就改用另一个向量模型，即使维度相同也不可混入旧索引；升级应使用新公开 ID 和显式重建流程。
5. PaddleOCR 任务使用平台任务 ID 映射，保存实际成员、上游任务 ID 及结果归属。创建时可选择健康成员，创建后查询、结果与凭据刷新继续绑定同一账号；JSONL 及页面关联保留，下载授权不能泄露平台采购 Token 或开放跨用户任务读取。

## 验收场景

1. 三个独立账号连续请求分配到 A/B/C；禁用 B 后不再向 B 发送。
2. 同一次请求 A 返回 429，B 成功；前端只收到 B 的结果、平台仅结算一次；A 在冷却期内被后续请求跳过。
3. `Retry-After` 秒值、日期、无效值、超大值和额度重置边界均有确定预期；通过可控时钟验证到期回池，不使用长时间 sleep。
4. A 凭据失效只隔离 A；通用 403 不误封整个池；所有成员冷却时返回最早恢复提示，不形成无限重试。
5. 显式模型路由不会在 A 失败但 B 健康时直接耗尽当前池；不因池内重试越权跨组、跨协议或绕过上游 retry veto。
6. 前端已收到流式正文后失败不换账号拼流，取消后不继续发送，绑定账号的会话与任务不跨账号错用。
7. Gateway 的真实 HTTP 429/401 早退路径更新正确成员；BYOK 故障不进入平台账号池，不偷偷切到平台付费凭据。
8. 重启与缓存重载保留冷却，成员删除/替换后旧请求结果不污染新成员；两实例共享冷却状态。
9. SQLite/MySQL/PostgreSQL 均执行状态持久化、选择、锁与恢复回归；全量后端/race、前端构建和类型检查通过。
10. 图片理解/生成/编辑、ASR、TTS、音频理解、视频理解和 OCR 各有真实 HTTP 契约回归；能力注册、实际适配器、目录声明一致。不支持某模态时在发送与预扣前明确拒绝。
11. 视频理解样例包含视频输入及问题，证明保留视频语义；有音轨理解宣称的模型另验音轨。不以视频生成任务或单张截图替代视频理解验收。
12. OCR 样例包含多页/表格或公式的结构保留，音频样例包含编码和流式/非流式输出；未提供的置信度、坐标或说话人信息保持缺失。
13. 语音操作限流只冷却相应作用域；共享资金耗尽作用于配置的 quota group。不同端点、地域、套餐权限的账号不会互相误用。
14. 图片/转写/文档任务创建成功后，轮询、下载及恢复均绑定正确成员；超时不明确的创建不重复发送，退款/结算只执行一次。
15. 媒体超限、畸形元数据、URL 重定向和过期/跨用户文件引用均被正确拒绝；跨账号重试的媒体可重放但不越权，日志中没有密钥或媒体正文。
16. SuperWagie 通过 LLMRouter 完成“文档解析/OCR、固定模型向量入库、查询向量化、阿里协议重排、带来源片段返回 Agent”的契约测试；测试分别断言数据结构，不能用 `/models` 列表代替。
17. Embedding A/B 两个账号切换后模型和向量空间一致；错误维度、批量 index 错乱或不可确认的模型版本明确失败，不能生成 ready 索引。
18. PaddleOCR 创建/轮询/JSONL 下载沿用正确成员与用户归属；已有 SuperWagie 索引在网关切换时触发预期的迁移保护，不自动清库、重建或替换模型。
